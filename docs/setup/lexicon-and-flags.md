# Remote flags, signed lexicon versions and device bans — setup, keys and runbook

PRD `19-admin-console.md` REQ-ADM-12 ("Flag changes reach clients within 5 min without a release; lexicon versions are
signed and reversible") and REQ-ADM-14 ("One confirm action bans account and device"); F9 in
`06c-features-platform.md` (crisis lexicon "versioned signed bundle … refreshed on sync"). Milestone A.
Wire contract: `contracts/api/v1.md` → "Remote config", "Crisis lexicon versions", "Device bans".

| Piece | Where | What it does |
|---|---|---|

## 1. What AK must set

| Where | Variable | Value |
|---|---|---|
| API env (secret) | `LEXICON_SIGNING_KEY` | The Ed25519 private key that signs lexicon versions: base64 of the 32-byte seed from `pnpm lexicon keygen` (or a PKCS#8 PEM, `openssl genpkey -algorithm ed25519`). **Unset in production = publishing off** (`503 signing_unavailable`); already published bundles keep being served. Unset in development/test = the public development key. The development key is refused in production. |
| App build define (public) | `AURA_BUNDLE_PUBLIC_KEYS` | Comma-separated base64 public keys the app trusts, from `pnpm lexicon keygen` / `pnpm lexicon public-key`. **Release builds without it never use a downloaded lexicon** (bundled v1 only) — they never trust the development key. Debug/profile builds without it trust the development key, so a local API works. |
| API env (optional) | `REMOTE_CONFIG_POLL_SECONDS` | 60–300, default 240: how often a foregrounded app re-fetches `/v1/config`. Keep ≤ 280 so a flip lands within 5 minutes. |
| API env (optional) | `REMOTE_CONFIG_CACHE_MS` | 0–30000, default 10000: how long one API instance reuses the built config document. |

`AURA_MASTER_KEY` (already required) also keys the install-id HMAC: rotating it makes existing device bans unmatchable
(they would have to be re-issued), so rotate it only with that in mind.

Release build, e.g.:

```sh
flutter build ipa --dart-define=AURA_API_URL=https://api.example --dart-define=AURA_BUNDLE_PUBLIC_KEYS=<base64 public key>
```

## 2. Key management

```sh
cd server/aura-api
pnpm lexicon keygen              # prints LEXICON_SIGNING_KEY=… (secret), AURA_BUNDLE_PUBLIC_KEYS=… (public), key id
pnpm lexicon public-key          # the public key / key id of the LEXICON_SIGNING_KEY in the environment or .env
pnpm lexicon public-key --dev    # the development key: keyId ba9afcf9c1f7ab25
```

- **Where the private key lives:** only in the API's environment (DigitalOcean app secret). Never in the repo, the app,
  the console or a log. The console never sees it — NestJS signs on publish.
- **The development key** is derived from a published string (`src/remote-config/signing.ts`, `DEV_KEY_LABEL`), so it
  is not a secret: use it only locally and in tests.
- **Rotation (planned):** (1) `pnpm lexicon keygen` → new pair; (2) ship an app release whose
  `AURA_BUNDLE_PUBLIC_KEYS` lists **old,new**; (3) once most phones have it, set the new `LEXICON_SIGNING_KEY` on the API
  and `POST /admin/lexicons/crisis/publish {version: <live>, reasonCode: "key_rotation", resign: true}` — the live
  version signed again with the new key; (4) a later release drops the old public key. Phones that still only know the
  old key keep their last verified version (or the bundled one) until they update — never an unverified one.
- **Compromise:** set a new `LEXICON_SIGNING_KEY` at once (publishing continues with the new key), re-sign the live
  version (`resign: true`), and ship a release that drops the compromised public key as soon as possible. Until then a
  holder of the old key could only sign lexicons that phones would also have to *download from the Aura API* (TLS);
  every change on the server side is in the audit log.
- **Signing locally (fixtures, offline checks):**
  ```sh
  pnpm lexicon sign ../../contracts/safety/crisis_lexicon.v1.json --dev --seq 1 --out /tmp/v1.signed.json
  pnpm lexicon verify /tmp/v1.signed.json                       # dev key; or --key <base64 public key>
  ```
  `sign` validates the schema and runs the contract vectors (plus `--vectors cases.json`) before signing. It never
  publishes: phones only get what the console publishes.

## 3. Publishing a lexicon version (Owner)

Through the console, or directly (staff token with TOTP):

1. `POST /admin/lexicons/crisis/versions/baseline` once, so version 1 (the bundled baseline) is stored and can be a
   rollback target.
2. Edit a copy of the live version (`GET /admin/lexicons/crisis/versions/:version`), bump `version`, add entries and
   **their test cases** (`vectors: [{text, verdict: crisis|soft|none, why}]`) → `POST /admin/lexicons/crisis/versions`.
   It is refused unless every contract vector and every own case passes, and en / te / te-Latn keep a crisis entry.
   Telugu and Tenglish entries still need the native + safe-messaging review (A9, REQ-SAFE-15).
3. `POST /admin/lexicons/crisis/test {version, samples: [...]}` — try real-life phrasings (verdicts only, nothing kept).
4. `POST /admin/lexicons/crisis/publish {version, reasonCode}`. Phones pick it up within `pollSeconds` while open, else
   at their next start / resume / sync.
5. **Roll back:** `POST /admin/lexicons/crisis/publish {version: <older>, reasonCode, allowCrisisRemovals: true}` —
   `allowCrisisRemovals` because an older version usually lacks crisis phrases the live one has (the API says how
   many). Removing a crisis term is Owner-only (PRD 19) and belongs in the review log.

Everything is in `GET /admin/lexicons/crisis` (`live`, `versions`, `history`) and in the audit log
(`lexicon_upload` / `lexicon_publish` / `lexicon_rollback`).

## 4. Flags and kill switches

- Flip: console → Config → the flag (`POST /admin/config/flags/:key {enabled, reasonCode}`, Owner, audited). The config
  document changes at once; open apps see it within `pollSeconds` + `REMOTE_CONFIG_CACHE_MS` (≤ 250 s by default).
- Per region (Quiet Together, the Lantern Hour wind-down): console → Kill switches → Per region
  (`POST /admin/config/regions/:key/:region/pause|resume {reasonCode}`, Owner, audited; Moderator reads). It edits
  `payload.pausedRegions`, which the server checks on every join; the flag off still pauses every region.
- What a flag does is its `feature_flags.description`, shown as is by the console: update it in the migration that
  changes the behaviour.
- Milestone A flags: `rooms_enabled` (kill switch: no new joins, `503 rooms_paused`; the app hides the join offers and
  says rooms are resting) and `rooms_pool_hi` (Hindi + Hinglish pool; the app offers an English room without a refused
  call). The app's bundled defaults: `rooms_enabled` on, `rooms_pool_hi` off.
- **Turning `rooms_pool_hi` on also tells the people who tapped "Tell me when they open"**: within a minute the worker's
  `pool-open-sweep` sends each of them one push ("Hindi and Hinglish rooms are open now.", their app language, the
  "Rooms & Lantern Hour" channel; quiet hours and the 2/day cap defer it) and forgets the request. Flipping it off and
  on again sends nothing twice. No push to an account with a scheduled deletion or an account / social ban or rooms
  pause. Needs the worker running (`pnpm start:worker`); contracts/api/v1-notifications.md §5.
- Adding a kill switch: a `feature_flags` row (migration, with `description`), `@KillSwitch({flag, code, message})` on
  the route(s) it must stop (`src/remote-config/kill-switch.ts`), a typed getter in `RemoteFlags`
  (`apps/mobile/lib/src/core/remote_config/remote_config.dart`) and a one-line read where the UI hides or greys it
  (`ref.watch(remoteFlagsProvider).yourFlag`). The server must refuse on its own: a flag on the phone never decides.

## 5. Device bans

- The **instant ban** (Minors & grooming SOP, REQ-ADM-14) should call
  `DeviceBansService.banDevicesForAccount(userId, reasonCode, { actor, reportId, tx })` in the same transaction as the
  `account_ban` sanction and the evidence hold (and put `installHashesForAccount(userId, tx)` into the evidence
  snapshot — "account and device IDs").
- Console (Owner): `GET /admin/devices?reportId=` → the account's devices; `POST /admin/devices/ban-account`
  `{reportId, reasonCode}`; `POST /admin/devices/:deviceId/ban`; `GET /admin/devices/bans`; lift with
  `POST /admin/devices/bans/:banId/lift {reasonCode}` (appeal upheld). A Moderator gets `403` and the attempt is
  audited (REQ-ADM-02).
- What the banned phone sees: "This device can't use Aura" (no reason), ask for a review (Grievance Officer email),
  delete the account, sign out, "I need help now". The account routes stay open so deletion always works.

**Limits and the later hardening.** The install id is random and kept in secure storage:

| Platform | Survives | Resets on |
|---|---|---|
| iOS (Keychain, `first_unlock`) | sign-out, app update, **delete + reinstall** | device erase; a restore to another device may carry it over |
| Android (Keystore-backed storage) | sign-out, app update | uninstall, "Clear storage" (Auto Backup is off for app data) |

A modified app can also simply not send it. The later hardening is **attestation**: Apple **DeviceCheck** (two
per-device bits set by the server, survive reinstall; needs a DeviceCheck key `.p8` from the Apple Developer account)
and Google **Play Integrity** (a verdict per request; needs a Google Cloud project with the Play Integrity API and the
app linked in Play Console). Then a ban can also set the DeviceCheck bit / refuse unattested requests. No server-side
fingerprinting (PRD F8).


## 6. The helpline directory (PRD 18 "Helplines by country")

The crisis sheet's numbers are a signed bundle of kind `helplines`, with the same key (`LEXICON_SIGNING_KEY` /
`AURA_BUNDLE_PUBLIC_KEYS`), envelope, `seq` and rollback rules as the lexicon. Every app build bundles
`contracts/safety/helplines.v1.json` (India: Tele-MANAS 14416 / 1-800-891-4416, 112, Childline 1098 under 18; US: 988;
elsewhere the local-emergency card), so the sheet works offline, signed out and before any download.

1. Console → **Helplines** → "Store the bundled directory" once (so going back to it is an ordinary rollback).
2. Copy a stored version's JSON, bump `version`, set `verifiedOn` to the day you called the numbers, edit, store. The
   API refuses a directory whose shown number isn't its dial string, a region without a line for everyone, or one that
   drops India or the US (the bundled regions phones require).
3. Open the version: the per-region list (adult / under 18) is exactly what phones will show. Then **Publish** (reason
   code). A changed or removed number needs "Allow removing numbers phones show now" (`allowRemovals`).
4. **Roll back** = publish an older version. Phones switch on their next config fetch (≤ `pollSeconds`).

**Safety:** a phone replaces its numbers only with a bundle whose signature verifies with a key it embeds, whose `seq`
is newer, whose content passes the same rules and whose vectors (region × adult/minor → dials) its own resolver
reproduces. Unsigned, tampered, replayed, unknown-key or malformed bundles are ignored: the last verified directory,
else the bundled one, stays. A release build without `AURA_BUNDLE_PUBLIC_KEYS` never downloads one.

Re-verify every number quarterly and before EU/UK/AU open (a wrong number is a P0 bug), and have te / te-Latn names
reviewed (docs/l10n/helplines-and-emails.md). CLI: `pnpm lexicon sign <helplines.json> --kind helplines [--dev]`,
`pnpm lexicon verify <bundle.json> --kind helplines`. Audit: `helplines_upload` / `helplines_publish` /
`helplines_rollback`.
