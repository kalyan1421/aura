# Aura API v1 (NestJS `server/aura-api`) — foundations slice

Base URL (local): `http://localhost:3310`. All `/v1/*` routes require `Authorization: Bearer <Supabase access token>`.
NestJS verifies the JWT (JWKS at `${SUPABASE_URL}/auth/v1/.well-known/jwks.json` when available, else HS256 with `SUPABASE_JWT_SECRET`) and uses `sub` as `user_id`.
Errors: `{ "code": "snake_case_code", "message": "human text" }` with a proper HTTP status.

Feature contracts: capsules → [`v1-capsules.md`](v1-capsules.md) · rooms and safety → [`v1-rooms.md`](v1-rooms.md) · notifications (F14: settings entity `notification_prefs`, push payloads and rules) → [`v1-notifications.md`](v1-notifications.md).

## Health
`GET /health` → `200 { "status": "ok", "db": "ok", "redis": "ok" }` (no auth)

## Onboarding / profile
`POST /v1/profile`
```json
{ "birthDate": "2006-04-17", "uiLocale": "te-Latn", "timezone": "Asia/Kolkata", "country": "IN", "ageSignal": "under18" }
```
- age < 13 on `birthDate` → `403 { "code": "under_13" }`, **nothing is stored**.
- otherwise upsert `profiles` (full DOB, DS-6), create `avatar_state` + `streak_state` rows (welcome rest day = 1) if missing → `200 { "profile": {...}, "snapshot": Snapshot }`.
- `uiLocale ∈ en | te | te-Latn | hi | hi-Latn`; `language_pool` derived: en→`en`, te/te-Latn→`te`, hi/hi-Latn→`hi`.
- **`ageSignal`** (optional, F8 REQ-ACC-04 / REQ-ACC-10): the platform age band the app read before sign-in (Apple Declared Age Range, Play Age Signals) — `"under13" | "under18" | "adult" | null`; anything else → `400 invalid_request`.
  - `"under13"` → `403 under_13`, **nothing is stored** (exactly like an under-13 DOB, whatever the DOB says).
  - `"under18"` → the account gets the **invisible under-18 protections** (minors lane, stricter moderation, analytics exclusion) even with an adult DOB: server-only `public.minor_signals`, read through `user_is_minor()` together with the DOB. It lasts until the youngest age in the band (13) would turn 18 — the user's local date + 5 years — and is only ever extended (a later `"under18"` never shortens it; `"adult"`, `null` or no field never clear it). Also recorded when the same request is refused with `409 birth_date_locked`.
  - `"adult"`, `null` or absent → the DOB alone decides.
  - Never returned by any endpoint and never visible to strangers (DS-10): the response is the same as without the field. The app sends the band only once per reading (it clears it after a `200`), so a later profile re-send (locale / timezone change) doesn't restart the 5 years.

`GET /v1/me/snapshot` → `200 Snapshot`

```ts
type Snapshot = {
  avatar: { stage: 'spark'|'ember'|'glow'|'radiance'|'constellation'; hue: number|null; isResting: boolean;
            ringCount: 0|1|2|3; glowLevel: 0|1|2|3; constellationStars: number; equippedCosmetics: string[] };
  streak: { glowStreak: number; lifetimeGlowDays: number; restBank: number; earnCounter: number; lastActiveDay: string|null };
  starlight: { total: number; today: number };
  serverTime: string;   // ISO, for client clock-offset
  auraDay: string;      // YYYY-MM-DD for the user's timezone
};
```

## Sync push (the only write path for personal data)
`POST /v1/sync/push`
```json
{
  "deviceId": "uuid",
  "mutations": [
    { "id": "uuidv7", "entity": "check_in", "op": "upsert", "deviceTs": "2026-10-08T10:00:00Z", "localDay": "2026-10-08",
      "payload": { "id": "uuidv7", "moodId": "anxious", "tags": ["study"], "noteCt": null, "source": "app",
                   "voicePath": null, "editedAt": "2026-10-08T18:30:00+05:30" } },
    { "id": "uuidv7", "entity": "habit", "op": "upsert", "deviceTs": "...", "localDay": "...",
      "payload": { "id": "uuidv7", "kind": "preset", "presetKey": "breathe", "name": null, "active": true } },
    { "id": "uuidv7", "entity": "habit_log", "op": "upsert", "deviceTs": "...", "localDay": "2026-10-08",
      "payload": { "id": "uuidv7", "habitId": "uuidv7" } },
    { "id": "uuidv7", "entity": "check_in", "op": "delete", "deviceTs": "...", "localDay": "...", "payload": { "id": "uuidv7" } }
  ]
}
```
Response `200`:
```json
{ "results": [ { "id": "uuidv7", "status": "applied" }, { "id": "uuidv7", "status": "duplicate" },
               { "id": "uuidv7", "status": "rejected", "reason": "unknown_mood" } ],
  "snapshot": { ...Snapshot } }
```
Rules:
- Max 200 mutations per request. Mutation `id` is the idempotency key (`sync_mutations` table, unique per user) → replays return `duplicate`.
- Each mutation is applied in its own savepoint inside one transaction; one bad mutation never blocks the rest.
- `check_in` / `habit_log` upserts append `starlight_ledger` rows per `contracts/rules/RULES.md` (eligibility, per-day awards, cap 60); **deletes never remove Starlight or glow days**.
- After applying, recompute `avatar_state` and `streak_state` from ledgers/active days (DS-5) and return the snapshot.
- `noteCt` is client-encrypted ciphertext (base64); the server never decrypts it.
- `check_in` payload fields `voicePath` (see "Media: voice notes") and `editedAt` (edits only, see "24-hour edit window" below) are optional.

## Resolved rules (implemented in server/aura-api, 23 Sep 2026)
- **DOB is locked after onboarding:** a later `POST /v1/profile` may change `uiLocale`, `timezone`, `country`, but a different `birthDate` → `409 birth_date_locked` (support-only change). The age-13 check uses **the user's own local date** (same rule as the app, so nobody is blocked on their 13th birthday because UTC lags); the DB `profiles_min_age` backstop allows 1 day of slack for zones ahead of UTC, and any violation maps to `403 under_13`.
- **Replays:** replaying an applied mutation → `duplicate`; replaying a rejected one → `rejected` with the original reason.
- **Habit credit** is once per habit per Aura day (ledger `source_id` derived from habit id + day), so un-log/re-log can't earn twice. A second log of the same habit on the same day under a new id → `rejected: already_logged`.
- **Local-day window:** `localDay` > 7 days behind the event's Aura day → `backfill_too_old`; > 2 days ahead → `invalid_local_day`; 1–2 days ahead or any backfill → stored, uncredited.
- **Edits** to an existing check-in change mood/tags/note/source (+ `voicePath`, see "Media: voice notes") only and never re-earn. Deleting a habit hard-deletes it and its logs; Starlight and glow days are untouched.
- **24-hour edit window (PRD F1 "edit for 24 h, delete anytime"):** an edit keeps the mutation's `deviceTs` / `localDay` equal to the **original** check-in time (if the first upsert never reached the server, the edit is applied as the insert and must be judged as the original event) and carries **`payload.editedAt`** = when the user made the edit (ISO 8601 with offset, device clock; anything else → `invalid_payload`; `null` = absent). When a `check_in` upsert hits an **existing** id, the window is judged by `editedAt` (fallback: the mutation's `deviceTs`), never by receive time — so an edit made offline at 23 h and synced at 30 h still applies: it must be within 24 h (inclusive, either side) of the check-in's stored `device_ts` **and** not more than 5 min ahead of server time (the ledger's clock-skew bound, RULES.md §2) → otherwise `rejected: edit_window_closed` (nothing changes). An edit with neither timestamp → `invalid_payload`. On a first insert `editedAt` is ignored (judged only by the local-day window above). Deletes are allowed any time.
- **Rings/glow** count distinct credited days of `breathe` / `sleep_on_time`.
- **Limits:** > 200 mutations → `400 too_many_mutations`; `noteCt` base64/base64url ≤ 16 KB; non-UUID mutation id → per-mutation `invalid_mutation_id` (not recorded).
- **Text length is counted in characters as people see them** — extended grapheme clusters (Node `Intl.Segmenter`), the same unit as the app's Dart `characters` — never UTF-16 units, so a Telugu or emoji text the app accepts is never rejected. A safety cap of 16 UTF-16 units per allowed character also applies (no real character comes close; it only stops combining-mark floods). Tags: ≤ 10 per check-in (more → `invalid_payload`), each trimmed, non-empty and ≤ **20** characters → else `rejected: tag_too_long`.
- **Per-mutation timezone (review fix):** every mutation may carry `"tz": "<IANA zone the device used to stamp localDay>"`. Backfill/eligibility are judged in that zone (profile tz only when absent), so travel never turns a live check-in into a backfill. An unknown zone → `rejected: invalid_tz`. The app also re-sends `POST /v1/profile` when the device zone changes (the snapshot's "today" uses the profile tz).
- **Habit limits (review fix):** each preset key at most once per user (`rejected: duplicate_preset_habit`, DB unique index as backstop); at most 3 **active** custom habits (`rejected: too_many_custom_habits`; deactivating one frees a slot). Legit daily max is therefore 59 Starlight; delete/re-create can gain at most +1 before the 60 cap. Habit names (custom, and a preset's optional name) are trimmed, non-empty and ≤ **30** characters (grapheme clusters, see above) → else `rejected: habit_name_too_long`; the DB backstop `habits_name_length` only bounds size (≤ 480 code points).
- **Retention:** `sync_mutations` rows older than 90 days are purged daily (worker `maintenance` queue, 03:17 UTC). Moderation retention runs daily at 03:29 UTC (job `retention`, `src/queues/retention.ts`), set in `public.safety_config`: the `moderation_actions` audit log keeps rows **3 years** (`moderation_audit_retention_days`, default 1096 days, 19 admin console `[LEGAL]`) and older rows are removed only through `public.prune_moderation_actions()` — a prefix of the hash chain, never the newest row, with the cut recorded in `moderation_audit_anchor` so `verifyAuditChain()` still passes (a plain `DELETE`/`UPDATE`/`TRUNCATE` still fails for every role); **closed reports** have no retention in the PRD, so `closed_report_retention_days` is `NULL` = **kept** (no deletion) until AK and the lawyer set one `[LEGAL]` — then a closed report is deleted that many days after it was resolved, unless its evidence hold still runs.
- **Auth:** Supabase user tokens are **ES256** — verified via JWKS (`kid`), issuer `${SUPABASE_URL}/auth/v1`, audience `authenticated`. HS256 only if `SUPABASE_JWT_SECRET` is set.

## Encryption key (DS-1 envelope)
`GET /v1/keys/data-key` → `200 { "keyId": "uuid", "dataKey": "base64-32-bytes" }`
Server generates a per-user 256-bit data key on first call, stores it **wrapped** with `AURA_MASTER_KEY` (AES-256-GCM) in `user_data_keys`, returns it unwrapped over TLS. Client keeps it in Keychain/Keystore and encrypts notes/capsules/media locally.

## Devices (FCM registration; sending is F14)
`PUT /v1/devices` → `204` (no body)
```json
{ "token": "<FCM registration token>", "platform": "ios" }
```
- `token`: string, 1–4096 chars. `platform ∈ ios | android`. Anything else → `400 invalid_request` (the message never echoes the token).
- Upserts `public.device_tokens` on `token` (unique): sets `user_id` to the caller, `platform`, `updated_at = now()`. Re-registering is idempotent; **a token that moves to another account is reassigned to it** (shared phones: the last signed-in account owns the install).
- A deleted auth user → `401 unknown_user`.

`DELETE /v1/devices` → `204` (no body), **idempotent**
```json
{ "token": "<FCM registration token>" }
```
- Deletes only where `token` **and** `user_id` = the caller match; an unknown token or another account's token is a silent no-op. Missing/empty token → `400 invalid_request`.

Rules:
- Tokens are device identifiers: never logged (API or app), never sent to analytics.
- When the app registers (apps/mobile `PushService`): only after the user answered the post-first-check-in explainer and the OS allows notifications (incl. iOS provisional), with a signed-in account whose profile reached the server; on iOS after the APNs token exists. Re-registers on FCM token refresh (and deletes the rotated-out token); offline → retried after the next successful sync. Sign-out → `DELETE` (best effort) then FCM `deleteToken()`. FCM auto-init is off until the user opts in.
- Push payloads are content-free: `{ "type": "<machine type>", "id"?: "<opaque id>" }` plus generic copy — never a mood, quadrant, room theme, pseudonym or user text (PRD Notifications, rule 3). F14 must prune rows FCM reports as `UNREGISTERED`.
- Sending (F14, implemented): see [`v1-notifications.md`](v1-notifications.md) — the worker sends only to registered tokens (a signed-out install has none), never during a scheduled deletion, and deletes a token as soon as FCM reports it `UNREGISTERED`.

## Account deletion (F8 REQ-ACC-11 · 7-day grace, then purge)
In-app, ≤ 3 taps from Settings, never via email. Online only (the app explains when offline).

`POST /v1/account/deletion` → `202 { "deletionScheduledFor": "2026-10-15T10:00:00Z" }`
- Schedules the purge **7 days** after the first request (grace period). **Idempotent:** a repeat returns the existing date and does not move it.
- Works whether or not a profile exists (an account that never finished onboarding can still be deleted).
- Immediately removes the caller's `device_tokens` (no pushes during the grace period).
- No request body (or `{}`; unknown keys are ignored). A body that is not a JSON object → `400 invalid_request`. Same for `DELETE`.
- A still-unexpired access token of an already purged account → `401 unknown_user`.
- Then, best effort (≤ 5 s, never failing the request), the stored Sign in with Apple token is revoked at Apple (see "Sign in with Apple token" below); anything left is revoked by the purge.

`GET /v1/account` → `200 { "deletionScheduledFor": "<ISO>" | null }` (`Cache-Control: no-store`). For an account closed for breaking the rules (see "Account closed") the body also carries **`"accountClosed": true`** — the key is absent otherwise, so the usual body is unchanged.

`DELETE /v1/account/deletion` → `200 { "deletionScheduledFor": null }` — cancels a scheduled deletion ("Keep my account"). Idempotent (no schedule → still `200`).
- Once the grace period has ended (`deletionScheduledFor ≤ now`, the purge may already be running) the account can no longer be kept → `409 { "code": "account_deletion_in_progress" }`; the schedule stays and every other route stays `403`. The app shows "This account is being deleted" and signs out.

While a deletion is scheduled, **every other `/v1/*` route returns `403 { "code": "account_deletion_pending" }`** (sync push, profile, snapshot, keys, devices). `/v1/account*` and `/health` keep working. Nothing new is written for the account during the grace period.

Purge (worker `maintenance` queue, at least daily): for each account whose `deletionScheduledFor ≤ now()`, in one transaction delete every personal row (profile incl. DOB, check-ins, habits, habit logs, Starlight ledger, avatar/streak state, sync mutations, wrapped data keys, device tokens, the under-18 signal flag), then revoke the Sign in with Apple token at Apple and delete it, then the user's objects under their prefix in the `private-media` bucket, then the Supabase Auth user. After the purge nothing about the person remains (no tombstone keyed by user id). With a 7-day grace and a daily job, the purge always completes well inside the PRD's 30 days.

Implementation (server/aura-api, 23 Sep 2026):
- Schedule table `public.account_deletions (user_id pk → auth.users on delete cascade, requested_at, scheduled_for)` — server-only (RLS on, no policies, no client privileges). The guard is one primary-key lookup per authenticated request; routes opt out with `@AllowPendingDeletion()` (only `/v1/account*`), `@Public()` routes (`/health`) are never checked.
- Job `account-purge` on the `maintenance` queue, **hourly** at :41 UTC (≤ 500 accounts per run). Per account: (1) one transaction deletes the rows of every public table with a `user_id` (`PERSONAL_TABLES` in `src/account/account-purge.ts`; the e2e suite fails when a new personal table is missing from it); (2) the user's `private-media` objects (name under `<user_id>/`, or `owner_id` = user) are deleted **through the Storage API** with the worker's `SUPABASE_SERVICE_ROLE_KEY` — never by deleting `storage.objects` rows (refused by `storage.protect_delete()`, and it would orphan the blobs); (3) one transaction scrubs GoTrue rows keyed by the id without an FK (`auth.audit_log_entries` whose actor or target is the user, `auth.flow_state`, session-less `auth.refresh_tokens`) and deletes the `auth.users` row via SQL (the API's `postgres` role holds DELETE on it), which cascades identities, sessions, MFA factors, one-time tokens and the `account_deletions` row. The Auth Admin API is deliberately not used: its delete writes a new audit entry containing the user's email and id.
- Cancel and purge both decide "due" on the DB clock under the per-user advisory lock, so a late "Keep my account" can never leave a half-purged account.
- Every step is idempotent; the schedule row survives until the last step, so a failed or interrupted run resumes next hour. If media exists but no service key is configured, the account is **deferred** (personal rows already gone; media + auth user wait) and the worker warns. Logs carry counts only (`due/purged/deferred/failed/rows/media/appleRevoked/appleAbandoned` + SQLSTATEs), never ids, emails, paths or tokens.
- Step 1b (between the personal rows and the media): the Sign in with Apple token (`apple_auth_tokens`, listed in `PERSONAL_TABLES` but skipped by step 1) is revoked at Apple, then its row is deleted. Apple unreachable, or no `APPLE_*` configuration on the worker → the account is **deferred** (personal rows already gone; token, media and auth user wait) and retried hourly for up to **72 h after the grace period** (`APPLE_REVOKE_RETRY_HOURS`); after that the token is dropped unrevoked (`appleAbandoned`, warned) and the purge finishes — still far inside 30 days. A token Apple refuses to revoke, or that can no longer be opened (master key replaced), is dropped at once.

### Sign in with Apple token (App Review 5.1.1(v) · PRD "Apple token revoked")
`POST /v1/account/apple-auth` → `204` (no body; `Cache-Control: no-store`)
```json
{ "authorizationCode": "<the one-time code from the native Sign in with Apple sheet>" }
```
- Sent **once**, by the app, right after a native Sign in with Apple succeeded with Supabase (the code is single-use and valid 5 minutes). NestJS exchanges it at `https://appleid.apple.com/auth/token` (client secret = an ES256 JWT signed with the team's Sign in with Apple key) and keeps only the **refresh token**, sealed with `AURA_MASTER_KEY` (AES-256-GCM, user id as associated data — like `user_data_keys`) in the server-only `public.apple_auth_tokens` (one per account; a newer sign-in replaces it — never revoked on replace, because revoking any token ends the whole authorization). Never logged, never returned.
- The code must belong to the account's own Apple identity (`auth.identities`, provider `apple`, matched on the id_token's `sub`) → else `409 apple_identity_mismatch` (nothing stored).
- `400 invalid_request` (no / empty / non-string `authorizationCode`, or a body that isn't an object) · `400 apple_code_rejected` (Apple refused the code: expired, already used, or issued to another app) · **`503 apple_unavailable`** — Apple isn't configured on this server (`APPLE_*` env missing, see `docs/setup/social-sign-in.md` §10) or can't be reached · `409 account_deletion_in_progress` once the purge owns the account (the new token is revoked at once) · `401 unknown_user` after the purge.
- **The app ignores every failure**: sign-in never depends on this call. Works during a deletion grace period and for a closed account (it is an `/v1/account*` route).
- Revoked (`https://appleid.apple.com/auth/revoke`, `token_type_hint=refresh_token`) when the deletion is requested (best effort) and by the purge (above). Apple on Android (browser OAuth through Supabase) returns no code to the app, so those accounts have no stored token yet (follow-up).

App behaviour (apps/mobile):
- Settings → Account → "Delete my account" → a screen that says what is deleted, the 7-day grace, that app-store subscriptions are managed (and cancelled) in the store, and that it needs a connection → confirm → `POST /v1/account/deletion` → shows the scheduled date → wipes the phone and signs out (the same wipe as sign-out).
- Signing in again during the grace period: the app calls `GET /v1/account`; if a date is set it asks "Keep my account?" → `DELETE /v1/account/deletion`, or "Let it go" → signs out again. A `403 account_deletion_pending` from any other route is treated the same way.
- Native Sign in with Apple (iOS): after the Supabase session exists the app sends Apple's `authorizationCode` to `POST /v1/account/apple-auth` once, in the background, and ignores the answer.

## Account closed (F9 · account-wide ban)
An account with an active `account_ban` sanction (moderator ban, the Minors & grooming instant ban, a confirmed under-13 closure) is closed: **every `/v1/*` route answers `403 { "code": "account_closed", "message": "This account was closed for breaking Aura's rules." }`** — sync push, profile, snapshot, keys, devices, media, rooms and the safety `POST`s — except:
- `/v1/account*` (status, deletion, "Keep my account", Apple token): the person can always see the status and **delete the account** (PRD F8 in-app deletion; export will live here too). `GET /v1/account` says `"accountClosed": true`.
- the read-only `GET /v1/safety/me`, `GET /v1/safety/reports`, `GET /v1/safety/blocks` (the closed state and the outcome inbox, `v1-rooms.md` §0);
- `/health` (public).

A pending deletion answers first (`403 account_deletion_pending` on the other routes). Active = not lifted, started, not ended (the same rule as the rooms guard); lifting the sanction reopens every route at once. The message never says why (19 admin console: no tipping off).

Implementation: global guard #3 `AccountClosedGuard` (`src/auth/account-closed.guard.ts`), after `AuthGuard` and `PendingDeletionGuard`; one lookup per authenticated request on the partial index `sanctions_user_idx (user_id, kind) where lifted_at is null`; routes opt out with `@AllowAccountClosed()`.

App behaviour (apps/mobile): after sign-in (after the deletion check) the app reads `GET /v1/account`; `accountClosed: true`, or a `403 account_closed` from any call later, shows a calm full-screen "This account is closed" page — no reason, the Grievance Officer and support contacts (from the build's `AURA_GRIEVANCE_*` / `AURA_SUPPORT_EMAIL`) to ask for a review, "Delete my account", "Sign out", and "I need help now" (help is never locked). Sync keeps the outbox and backs off; nothing is lost on the phone until the person signs out or deletes.

## Media: voice notes (F1 · DS-1 · bucket `private-media`)
Voice notes are recorded and **encrypted on the device** with the per-user data key (AES-256-GCM, the same envelope as notes; associated data = the check-in id) before anything leaves the phone. The server and Storage only ever see ciphertext (`application/octet-stream`). Clients never touch the bucket directly: NestJS (service role) signs short-lived URLs.

Both routes: `Authorization: Bearer <access token>` like every `/v1` route (`401 unauthorized`; `403 account_deletion_pending` during a deletion grace period), responses carry `Cache-Control: no-store`, and when Storage cannot be used — no `SUPABASE_SERVICE_ROLE_KEY` configured on the API, or Storage unreachable / erroring — they answer **`503 { "code": "media_unavailable" }`** (retry later with backoff; the check-in itself is never blocked, see below).

`POST /v1/media/upload-url`
```json
{ "kind": "voice", "recordId": "<check-in uuid>", "bytes": 412345 }
```
→ `200 { "path": "<user_id>/voice/<recordId>", "uploadUrl": "https://…", "expiresAt": "<ISO>" }`
- `kind ∈ voice` for check-ins; capsule media uses `capsule_voice` / `capsule_photo` (see `v1-capsules.md` §5). `recordId`: a UUID (any case; `path` is always lower-case). `bytes`: the ciphertext size, an integer 1 – 1,048,576 (60 s of AAC at ≤ 64 kbps plus GCM overhead fits well under 1 MB); larger → `400 media_too_large`; not a positive integer, unknown `kind`, bad `recordId` → `400 invalid_request`.
- `path` is deterministic per record, so a retried upload overwrites the same object (upsert). Use the returned `path` verbatim (in `voicePath` and for downloads).
- `expiresAt` is **10 minutes** out: stop using the URL then and ask for a new one. (Storage's own upload-token lifetime is a project-wide setting — 2 h by default, not settable per URL — so the server reports the shorter of the two.)
- Upload = one `PUT <uploadUrl>` with the raw ciphertext as the body and `Content-Type: application/octet-stream`. No `Authorization`/`apikey` header (the token is in the URL's query) and no `x-upsert` header needed (upsert is baked into the token; sending `x-upsert: true` is harmless). Success = `200 { "Key": "private-media/<path>" }`; anything else → request a fresh URL and retry.
- `uploadUrl` / `downloadUrl` are absolute URLs on the API's `SUPABASE_URL` (`http://127.0.0.1:55521/storage/v1/…` locally). Local builds whose Supabase host differs (Android emulator `10.0.2.2`) replace the scheme+host with their own `SUPABASE_URL`; path and query stay as they are.
- `bytes` is checked at request time only: Storage does not enforce the declared size per object (the bucket falls back to the global 50 MiB limit), so the app must never upload more than it declared.

`POST /v1/media/download-url`
```json
{ "path": "<user_id>/voice/<recordId>" }
```
→ `200 { "downloadUrl": "https://…", "expiresAt": "<ISO>" }` — only for paths under the caller's own `<user_id>/` prefix; anything else (another user's prefix, `..`, empty segments, odd characters, or an own path that does not exist) → `404 not_found` (never reveals whether it exists). A non-string / missing `path` → `400 invalid_request`.
- `expiresAt` is **5 minutes** out. `GET <downloadUrl>` (no headers) returns the ciphertext bytes; decrypt on the device.

Check-in payload (sync push): `check_in` upserts may carry **`"voicePath": "<user_id>/voice/<id>" | null`**.
- The path must equal `<caller user_id>/voice/<check-in id>` (case-insensitive; stored lower-case) → any other value, whatever its type, → `rejected: invalid_voice_path` (DB backstop: CHECK `check_ins_voice_path_shape`). The server does not check that the object exists.
- The app pushes a check-in with a voice note **only after the upload succeeded** (like `needsNote`, the outbox row waits for its media). If the upload keeps failing, the check-in itself is never blocked: after the outbox gives up on the media it pushes without `voicePath` and keeps the recording on the phone for a later edit.
- An edit (upsert of an existing id) replaces `voice_path` like the other fields; `null` removes the reference (the object is deleted by the server best-effort). **Omitting `voicePath` on an edit keeps the stored value** (so a build or device that doesn't know about voice notes never drops one); send `null` to remove it. Voice edits follow the 24-hour edit window like any edit (`edit_window_closed` changes nothing and deletes nothing).
- Deleting a check-in (`op: delete`) also deletes its voice object (best-effort; the account purge removes anything left under the user's prefix).
- Voice notes are not crisis-scanned in v1 (PRD F1); edit/delete rules are the same as for notes.

App behaviour (apps/mobile):
- Capture in check-in details (and within the 24 h edit): up to 60 s AAC/m4a, auto-stop at 60 s with a calm note; the first mic tap shows the rationale from the PRD permissions section (`15-permissions.md`) before the OS prompt; denied → "Voice is off" with a Settings link. Save is never blocked by voice.
- The recording is sealed on the phone with the per-user data key (AES-256-GCM, associated data = check-in id) in a private, backup-excluded `voice/` folder; if no key exists yet it stays raw only in that folder and is sealed before any upload. Nothing raw is ever uploaded.
- Push order per record: upload-url → PUT → the check-in upsert with `voicePath`. A record's mutations always go out in order (a later one waits while an earlier one backs off), and voice uploads go first in their batch. After 10 failed uploads the check-in is pushed without `voicePath` and the file is kept for a later edit; `media_too_large` gives up at once.
- Playback fetches lazily via `download-url`, decrypts to a temp file that is deleted when the screen closes. Sign-out and account deletion wipe all voice files, drafts and temp copies.

Implementation (server/aura-api, 23 Sep 2026):
- Object deletes happen **after the push commits** (a rolled-back push never loses a recording), in one Storage API call, and only for paths no check-in of the user references at the end of the push (clear-then-re-add inside one batch deletes nothing). Best-effort: a missing service key, a Storage error or a 5 s timeout is logged as a warning with counts only (never ids or paths) and never changes the push result. Replays (`duplicate`) delete nothing.
- App ordering: don't upload a new recording for a check-in while a push that clears its `voicePath` is in flight — that push's post-commit delete would remove the fresh upload. Upload after the response, then push the edit with `voicePath`.
- An upload whose check-in is never stored (e.g. the push was `rejected: backfill_too_old`) stays in the bucket until the account is purged; no sweeper yet.
